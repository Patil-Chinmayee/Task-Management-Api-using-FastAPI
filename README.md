Task Management API using FastAPI
A REST API for managing personal tasks, built with FastAPI, SQLAlchemy, Pydantic, and JWT-based authentication. Users can register and log in, then create, view, update, and delete tasks associated with their account.
Project status: This README documents the code currently present in the repository. See Known Issues and Recommended Improvements before using the project beyond local development.

Features
- User registration with password hashing using Argon2.
- User login and JWT access-token generation.
- OAuth2 bearer-token support through the /users/token endpoint.
- Create, list, retrieve, update, and delete tasks.
- Task records associated with the authenticated user.
- SQLAlchemy ORM for database operations.
- Pydantic request schemas for input parsing and validation.
- Interactive API documentation generated by FastAPI.

How It Works
1. Application startup: main.py creates the FastAPI application, creates database tables through SQLAlchemy metadata, and registers the task and user routers.
2. Database access: routes use Depends(get_db) to obtain a SQLAlchemy session. The dependency closes the session when the request finishes.
3. Registration: /users/register checks whether the username exists, hashes the password, and saves the user.
4. Login: /users/login or /users/token verifies the password and returns a signed JWT access token.
5. Authentication: protected task endpoints use auth.get_current_user. It extracts the bearer token, verifies the JWT, resolves the username, and loads the user from the database.
6. Task ownership: new tasks are created with the authenticated user's ID. The list endpoint filters tasks by that ID. The single-task, update, and delete endpoints are intended to check ownership.
Requirements
- Python version supported by the project configuration (pyproject.toml currently specifies Python 3.14 or newer).
- A database supported by the configured SQLAlchemy URL. PostgreSQL is supported by the included psycopg2-binary dependency.

If you use a Python version other than the version declared in pyproject.toml, update the project requirement after verifying compatibility.
Setup and Installation
1. Clone or extract the repository
git clone <repository-url>
cd Task-Management-Api-using-FastAPI
If you downloaded a ZIP, extract it and open a terminal in the project directory.
2. Create and activate a virtual environment
Windows (PowerShell):
python -m venv .venv
.\.venv\Scripts\Activate.ps1
macOS / Linux:
python3 -m venv .venv
source .venv/bin/activate
3. Install dependencies
python -m pip install --upgrade pip
pip install -r requirements.txt
Alternatively, if using uv:
uv sync
4. Configure environment variables
Create a local .env file in the project root. Do not commit real credentials or signing keys.
DATABASE_URL=postgresql+psycopg2://<username>:<password>@localhost:5432/task_management
SECRET_KEY=replace-with-a-long-random-secret
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
Create the task_management database in PostgreSQL before starting the application, and replace the placeholder username, password, host, and database name with your own values.

DATABASE_URL must match the SQLAlchemy database URL format for the database driver you use. The code's settings require DATABASE_URL, SECRET_KEY, and ALGORITHM; the token expiry defaults to 30 minutes.

API Reference
All routes are defined in the router modules. The examples below reflect the current route paths and payload schemas.
Users
Method	Endpoint	Authentication	Purpose
POST	/users/register	Not required	Register a new user
POST	/users/login	Not required	Log in with JSON credentials and receive a token
POST	/users/token	Not required	OAuth2 form-based login and receive a bearer token


Register — POST /users/register

Request body:
{
  "username": "alex",
  "password": "choose-a-strong-password"
}
Successful response includes the new user's id and username. The password hash is not returned.

Login — POST /users/login

Request body:
{
  "username": "alex",
  "password": "choose-a-strong-password"
}
Successful response format:
{
  "token": "<jwt-access-token>",
  "token_type": "bearer"
}
OAuth2 token — POST /users/token

This endpoint expects form fields, not a JSON body:
username=alex
password=choose-a-strong-password
Successful response format:
{
  "access_token": "<jwt-access-token>",
  "token_type": "bearer"
}
Tasks
All task endpoints require a valid bearer token.
Method	Endpoint	Purpose
POST	/tasks/create-task	Create a task for the authenticated user
GET	/tasks/get-task	List the authenticated user's tasks
GET	/tasks/get-task-by-id/{id}	Retrieve a task by ID
PUT	/tasks/update-task?id={id}	Update a task by ID
DELETE	/tasks/delete-task?id={id}	Delete a task by ID


Create a task — POST /tasks/create-task
{
  "title": "Prepare interview notes",
  "description": "Review FastAPI and SQLAlchemy",
  "completed": false
}
The API assigns user_id from the authenticated user; clients should not provide it.

List tasks — GET /tasks/get-task

Returns tasks filtered by the authenticated user's ID.

Get one task — GET /tasks/get-task-by-id/1

Replace 1 with the task ID. The intended behavior is to return the task only if it belongs to the current user.

Update a task — PUT /tasks/update-task?id=1

The id is a query parameter. The request body uses the same schema as task creation:
{
  "title": "Prepare updated interview notes",
  "description": "Review authentication and API design",
  "completed": true
}
Delete a task — DELETE /tasks/delete-task?id=1

The id is a query parameter. The intended success response is:
{
  "message": "Task is deleted"
}
Common response codes
Status	Meaning
200	Request succeeded
400	Registration attempted with an existing username
401	Missing, invalid, or expired authentication credentials
403	Authenticated user is not permitted to access the task
404	Requested resource was not found (once the not-found checks are corrected)
422	Request validation failed or required fields are missing


Exact responses can vary with FastAPI defaults and the current implementation.
Authentication
The application uses JWT bearer authentication.
1. Register a user.
2. Log in to receive a token.
3. Send the token in the Authorization header for protected endpoints:
Authorization: Bearer <jwt-access-token>
The JWT subject (sub) is set to the username and the token includes an expiry (exp). The configured signing algorithm and secret key are read from environment settings. Passwords are stored as Argon2 hashes rather than plaintext.
Example Workflow
1. Open /docs.
2. Call POST /users/register.
3. Call POST /users/login with the same credentials.
4. Copy the returned token.
5. In Swagger UI, click Authorize and provide the bearer token if prompted. The OAuth2 password flow is configured with /users/token, so use the form-based token endpoint if the Authorize dialog expects OAuth2 form login.
6. Create a task, list tasks, and test update/delete operations.
For command-line testing, you can use curl or an API client such as Postman. Ensure the token is sent on all task requests.
Database Design
users
Column	Type	Notes
id	Integer	Primary key, indexed
username	String	Required by the model
password	String	Stores the password hash


tasks
Column	Type	Notes
id	Integer	Primary key, indexed
title	String	Required by the model
description	String	Model column is non-nullable
completed	Boolean	Defaults to False
user_id	Integer	Foreign key referencing users.id


Each task is associated with a user through tasks.user_id. The current model does not declare an ORM relationship or database cascade behavior.
Known Issues and Recommended Improvements
The following are implementation findings from reviewing the repository. They should be addressed before treating the API as production-ready:
1. Check for missing tasks before accessing attributes. In the get-by-ID, update, and delete endpoints, the code checks task.user_id / task_exist.user_id before checking whether the query returned None. A nonexistent ID can therefore cause a server error instead of a clean 404.
2. Correct the user-not-found exception argument. get_current_user uses HTTPException(..., details="User not found"); FastAPI expects detail, not details.
3. Handle list-task errors consistently. The list endpoint catches all exceptions, prints them, and returns nothing. Prefer logging and a deliberate HTTP error response, without exposing internal exception details.
4. Make ownership checks consistent and robust. Querying a task by both its ID and the authenticated user's ID can simplify access control and avoid revealing whether another user's task exists.
5. Align the task schema and database nullability. TaskCreate.description is typed as str but defaults to None, while the database column is non-nullable. Decide whether description is required; then make the Pydantic schema and ORM model agree.
6. Add response schemas. Define separate Pydantic response models for users and tasks to make the API contract explicit and avoid accidentally exposing fields.
7. Add database migrations. Base.metadata.create_all() is convenient for a small demo but does not manage schema changes. Consider Alembic for migrations.
8. Strengthen data constraints. Consider a unique constraint on users.username, field length limits, password policy, and indexes appropriate to common queries.
9. Review security and token handling. Keep .env out of version control, use a high-entropy secret, use HTTPS outside local development, validate token configuration, and consider refresh-token/revocation requirements.
10. Use consistent endpoint conventions. REST-style paths such as POST /tasks, GET /tasks, GET /tasks/{id}, PATCH or PUT /tasks/{id}, and DELETE /tasks/{id} would be easier to understand and document.
11. Add automated tests. Cover registration, duplicate usernames, login success/failure, missing/expired tokens, CRUD operations, and cross-user task access.
12. Review dependency/version requirements. pyproject.toml declares Python >=3.14, which may be stricter than necessary. Confirm the intended Python version and keep pyproject.toml and requirements.txt aligned.
13. Use timezone-aware UTC timestamps for JWT expiry. Consider datetime.now(timezone.utc) rather than the naive datetime.utcnow() pattern.
14. Add validation and operational safeguards. Configure structured logging, database connection error handling, rate limiting for authentication, and deployment-specific settings.
